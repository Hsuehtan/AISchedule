### 0.1 规范性用语

- **必须**：P0 发布条件，不满足则不应上线。
- **应该**：强烈建议满足；若延期，必须记录原因和替代方案。
- **可以**：可选增强，不影响 P0 闭环成立。
- **AI 写操作**：任何由 Agent 发起、可能改变用户持久化数据的操作。
- **手动操作**：用户通过明确 UI 控件直接发起的创建、编辑、完成、恢复或删除操作。
- **AI 能力接口**：会调用 AI 或模型 API 的产品功能接口；每个接口必须绑定唯一能力编码和积分成本。
- **AI 积分**：后端用于控制 AI 能力使用额度的业务余额，MVP 暂不向用户展示具体余额和单次成本。
- **extra 字段**：所有持久化数据对象统一保留的 Object（obj）扩展字段，默认值为 {}。

### 0.2 优先级定义

| 优先级 | 定义 | 首次上线 |
|---|---|---|
| P0 | 验证核心价值闭环所必需，或保障数据正确性、用户控制权所必需 | 包含 |

## 1. 产品概述

### 1.1 一句话定位

一款面向普通 C 端用户的 AI 待办管理工具：用户只需说出不同模糊度的目标，AI 通过对话澄清、拆解并推荐优先级；用户确认后，系统将结果转化为可持续管理和完成的待办。

### 1.2 用户问题

用户身边同时存在工作、生活、家庭、爱好等多个领域的事情，但精力有限，往往只有一个模糊目标，难以自行完成以下工作：

1. 想清楚达成目标需要做什么。
2. 把目标拆成具体、可执行的事项。
3. 为事项设置合理的初始优先级。
4. 把 AI 给出的方案保存为可持续管理的任务。
5. 在后续实践中修改、完成、恢复或删除这些任务。

传统待办产品要求用户先完成思考与拆解，再逐项录入；通用 AI 助手可以提供方案，却通常止于文字回答，缺少持久任务状态和后续管理闭环。

### 1.3 产品解决方案

产品由两个连续循环组成：

1. **规划循环**：用户表达目标或操作意图，AI 根据模糊度进行澄清，生成计划或 Action 草稿，用户确认。
2. **执行循环**：确认后的项目和任务进入熟悉的待办界面，用户通过手动操作或继续对话进行管理，直到任务被处理。

产品采用“待办优先、对话增强”的交互结构，而不是以聊天窗口作为主界面：

- 首页首先让用户识别出这是待办管理产品。
- AI 对话以底部浮层承载，不改变用户对待办工具的基本操作习惯。
- 包括首次进入在内，用户登录后默认看到待办首页；AI 由用户通过 Smart Inbox 或底部输入入口主动唤起。

### 1.4 核心差异化

| 对比对象 | 其主要能力 | 本产品的差异 |
|---|---|---|
| 传统待办产品 | 记录、分类、提醒、完成 | 在记录之前帮助用户澄清和拆解模糊目标 |
| 通用 AI 助手 | 生成建议、清单或文档 | 将建议转化为持久任务，并承接后续修改、完成和跟进 |
| AI 自动规划工具 | 替用户排序或安排 | AI 只提供工具和建议，最终决定权始终属于用户 |

### 1.5 产品原则

1. **用户主权**：AI 提供工具和建议，不替用户作最终决定。
2. **确认后写入**：MVP 中所有 AI 写操作必须经过 Action 确认卡。
3. **熟悉优先**：保留传统待办的任务列表、项目筛选和完成操作。
4. **按模糊度澄清**：信息充分时少问，信息不足时追问；不得机械地强制走固定问卷。
5. **建议可编辑**：AI 推荐的任务、项目、时间和优先级都可被用户修改或拒绝。
6. **失败时不写入**：无法确定对象、执行失败或状态冲突时，不得产生部分或隐式写入。
7. **先可信再自动**：未来是否允许某类 Action 直接执行，只能由持续评测结果决定。
8. **模型调用才扣分**：不调用 AI 或模型 API 的能力不扣积分；需要调用的接口必须先完成统一积分校验。

## 2. 目标用户与核心任务

### 2.1 目标用户

首批目标用户是符合以下行为特征的普通 C 端用户：

- 同时管理工作、生活、家庭、爱好等约 3 至 5 个事项领域。
- 经常只有目标，没有清晰步骤，例如“周末去露营”“准备搬家”“开始健身”。
- 已经或愿意使用 ChatGPT、DeepSeek、豆包等 AI 助手获取方案。
- 曾把 AI 输出复制到备忘录、截图或手动转录到待办工具，但后续容易遗忘。
- 不希望学习复杂项目管理方法，也不希望把全部操作迁移到聊天窗口。

### 2.2 非目标用户

MVP 不以以下人群或场景为主要设计对象：

- 需要多人协作、权限、审批和组织管理的企业团队。
- 需要甘特图、资源排期、关键路径等能力的专业项目经理。
- 希望 AI 完全自主决定优先级和每日计划的用户。
- 只需要开放式知识问答、不需要任务落地的用户。

### 2.3 用户待办任务 JTBD

> 当我脑中只有一个目标，或有一批零散事项时，我希望通过几句自然语言让系统帮我想清楚并形成可执行待办，这样我不需要自行拆解和反复整理，也不会让 AI 给出的方案停留在聊天记录里。

### 2.4 MVP 核心价值闭环

MVP 必须完整支持以下闭环：

    表达模糊目标
        ↓
    AI 判断信息是否充分
        ↓
    必要时澄清或让用户选择
        ↓
    生成可编辑的计划 / Action 草稿
        ↓
    用户明确确认
        ↓
    创建并持久化项目与任务
        ↓
    用户后续查看、修改、完成或恢复任务

如果产品只能生成清单但不能承接管理，或只能管理任务但不能完成目标澄清，则 MVP 核心价值均不成立。

## 3. 产品目标、成功定义与非目标

### 3.1 MVP 产品目标

1. 新用户能够通过一次自然语言对话创建一批对其真实目标有用的待办。
2. 用户能清楚理解 AI 将执行什么，并在确认前修改或取消。
3. 确认后的任务能进入稳定、熟悉的待办管理界面。
4. 用户能在后续真实完成、修改、恢复或删除这些任务。
5. 系统能采集足够的结构化评测数据，为未来按 Action 类型开放直接执行提供依据。
6. 所有 AI 能力使用均经过统一积分校验和流水审计，为后续额度与商业化策略保留稳定底座。

### 3.2 MVP 成功定义

#### 核心激活事件

新用户注册后，主动通过 AI 对话确认并成功创建至少一批任务。

#### 核心价值事件

用户在后续使用中，对这批任务至少完成一次真实管理行为，包括：

- 标记完成；
- 修改标题、项目、优先级、截止时间或提醒；
- 恢复已完成任务；
- 删除不再需要的任务。

#### 建议观测漏斗

1. AI 入口曝光。
2. 用户提交目标或操作指令。
3. AI 积分校验通过。
4. AI 完成澄清或直接生成草稿，并完成积分结算。
5. Action 确认卡展示。
6. 用户确认并成功执行。
7. 任务进入列表。
8. 用户在后续会话中管理或完成该任务。

具体转化率和留存率阈值尚未确认，必须在上线评审前补充；但 P0 必须完成上述事件采集。

### 3.3 安全与信任指标

| 指标 | P0 要求 |
|---|---|
| 未经用户确认的 AI 写入 | 必须为 0 |
| 重复点击导致重复执行 | 必须为 0 |
| 批量创建出现部分成功、部分失败 | 必须为 0；采用原子执行或明确回滚 |
| AI 声称成功但实际未写入 | 必须为 0 |
| 无法唯一确定操作对象时直接修改 | 必须为 0 |
| Action 的确认、取消、修正和失败 | 必须可追踪 |
| 未经积分校验调用收费模型接口 | 必须为 0 |
| 同一 AI 请求重复扣分或余额小于 0 | 必须为 0 |
| 未调用模型却扣除 AI 积分 | 必须为 0 |

### 3.4 MVP 非目标

- 不替用户选出每天“最值得完成”的 3 至 5 件事。
- 不自动改变用户确认过的优先级、截止时间或项目归属。
- 不把产品做成通用聊天机器人。
- 不提供复杂专业项目管理。
- 不在 MVP 中允许 Agent 绕过确认卡直接写入。
- 不在 MVP 中向用户展示或销售 AI 积分。

## 4. MVP 功能边界：P0

### 4.1 P0 功能总表

| 编号 | 模块 | P0 功能 | P0 验收摘要 |
|---|---|---|---|
| P0-01 | 用户身份与数据持久化 | 注册、登录、退出、用户数据隔离与跨会话保留 | 用户重新进入后仍能看到自己的项目、任务和待处理 AI 状态 |
| P0-02 | 待办首页 | 全部/项目筛选、待完成列表、已完成折叠、空状态、固定 AI 输入入口 | 用户第一眼可识别为待办产品，并能查看和处理任务 |
| P0-03 | 手动任务管理 | 新建、编辑、完成、恢复、软删除、撤销 | 所有状态变化正确持久化并有明确反馈 |
| P0-04 | 项目管理 | 新建、改名、归档、待完成任务计数 | 归档不删除任务；无项目任务仍可管理 |
| P0-05 | 自然语言输入 | 文字输入、语音转写、转写结果确认/重试 | 文字与语音进入同一 Agent 逻辑 |
| P0-06 | AI 对话浮层 | 用户输入、AI 回答、选择/澄清、Action 确认四类消息 | 不同消息职责清楚，线程可持续对话 |
| P0-07 | 目标澄清与任务拆解 | 按模糊度追问、生成项目建议、任务列表和优先级建议 | 建议可编辑；未确认前不创建数据 |
| P0-08 | AI 任务操作 | 通过自然语言创建、修改、完成、恢复和软删除任务 | 无论 Action 类型，MVP 均先展示确认卡 |
| P0-09 | Action 确认与执行 | 展示操作对象、字段变化、结果影响；确认后原子执行 | 确认是唯一 AI 写入网关 |
| P0-10 | Smart Inbox | 展示待澄清、待确认和待办归属/时间/提醒整理等真实状态，可折叠 | 无待处理状态时展示通用 AI 入口；“一键整理”进入草稿/确认流程 |
| P0-11 | 反馈与异常 | 成功、失败、撤销、AI 积分不足或服务不可用状态 | 不展示积分余额、Token、模型成本等内部信息 |
| P0-12 | 评测与审计 | 记录意图、候选对象、草稿、用户修正、确认、执行结果和模型版本 | 支持按 Action 类型评估未来自动化资格 |
| P0-13 | 基础隐私与无障碍 | 数据隔离、敏感内容保护、可访问标签、焦点和颜色替代信息 | 个人任务不串号；核心操作不只依赖颜色 |
| P0-14 | AI 积分与接口计费 | User 积分余额、能力成本配置、调用前校验与预占、结算/退款流水和幂等 | 不调用模型不扣分；AI 已产出后用户取消仍扣分 |

### 4.2 P0-01 用户身份与数据持久化

P0 必须提供稳定的用户身份，使任务和对话状态能够跨会话保留。

产品要求：

- 用户只能访问自己的项目、任务、会话和 Action。
- 登录后恢复上次有效数据状态。
- 退出后不得在未授权状态展示个人任务内容。
- 登录页设计稿中的“2 件事，已经等你确认”和“写周报”等内容只是非用户、不可操作的静态产品演示，不从任何真实账号加载，不代表访客已有任务；完成认证后必须完全替换为当前用户数据。
- 用户账号必须保存 AI 积分可用余额，但 MVP 不在用户界面展示余额。
- P0 注册只要求用户名和密码，手机号选填；不采集邮箱，不使用邀请码。
- P0 登录仅支持用户名 + 密码；用户名只作为过渡登录标识，不作为 C 端展示名称。
- 昵称默认“用户”，支持 1-10 个中英文字母，不做唯一校验；C 端可修改昵称但不提供改密入口。
- 未验证手机号不能用于登录或找回密码；后续由独立验证码 Provider 增加手机号身份。
- 管理员可通过 CLI 修改密码并撤销用户全部旧 Session；验证码、微信登录和企业单点登录不属于 P0。

### 4.3 P0-02 待办首页

首页保持当前 UI 的任务优先结构，至少包含：

- 当前日期和星期；
- 页面标题及当前范围摘要；
- “全部”和活跃项目横向筛选；
- 待完成任务列表；
- 已完成任务折叠区及数量；
- Smart Inbox 状态区；
- 固定在底部的文字/语音 AI 输入入口；
- 手动新建任务入口。

列表规则：

- MVP 不提供首次使用引导；第一次进入与后续进入均直接展示可操作的待办首页，不自动弹出对话或播放引导动效。
- “全部”展示用户全部未删除任务。
- 项目筛选只展示属于该项目的任务。
- 无项目任务只在“全部”中显示。
- 首页标题中的 N 表示当前筛选范围内 status = pending 的任务总数；“今天先处理”是界面语气，不代表只筛选今日任务。
- 已完成任务从待完成区移到底部折叠区。
- 已恢复任务回到待完成区。
- 已完成数量按当前筛选范围计算，默认折叠；展开后可查看完成任务并手动恢复。
- 任务行必须同时区分计划执行时间、Deadline 和提醒：左侧显示 scheduled_at 的紧凑标签，副文案显示 Deadline 与提醒。
- 待完成任务采用确定性时间线排序：已过计划时间优先，其后按 scheduled_at 从近到远，未排期任务最后；同一排期下按优先级和创建时间稳定排序。
- 页面摘要必须与当前实际展示范围一致。
- 选中项目时，页面标题展示项目名称及该项目的待完成数量。
- P0 不由 AI 自动挑选或隐藏“更值得做”的任务。
- 最终 UI 保留“今天先处理 N 件事”的界面文案，但该文案不表示 AI 已替用户筛选每日重点；数量和辅助摘要必须按当前范围真实计算。
- 当前筛选范围没有待完成任务时，标题显示“今天已经清空”，并展示完成态空页面和“设置一件新事情”入口；点击后打开创建入口，项目筛选、Smart Inbox 和已完成折叠区仍可访问。

### 4.4 P0-03 手动任务管理

任务字段：

| 字段 | P0 要求 |
|---|---|
| 标题 | 必填 |
| 所属项目 | 可选；为空时属于“无项目” |
| 描述 | 可选 |
| 优先级 | 高 / 中 / 低 / 未设置 |
| 计划执行时间 | 可选；用于任务行左侧“09:30/今天/周五/待定”等排期展示 |
| 截止时间 | 可选 |
| 提醒时间 | 可选 |
| 状态 | 待完成 / 已完成 / 已删除 |

手动操作规则：

- 用户点击任务主体打开编辑浮层。
- 用户点击保存后才持久化表单修改。
- 手动新建或编辑保存成功后，关闭编辑浮层，并刷新当前筛选范围的任务列表、数量和页面摘要。
- 保存失败时保留用户已填写内容并允许重试。
- 用户点击完成控件可直接完成；完成后提供撤销。
- 用户可以恢复已完成任务。
- 删除采用软删除，并提供短时撤销。
- 用户通过明确 UI 控件发起的手动操作，不需要再经过 AI Action 确认卡。
- 提醒时间的实际系统通知交付方式仍待平台方案确认。

### 4.5 P0-04 项目管理

P0 的“项目”是轻量任务分组容器，不等同于专业项目管理。

必须支持：

- 手动新建项目；
- 修改项目名称；
- 归档项目；
- 查看项目下待完成任务数量；
- AI 计划确认后按用户确认结果新建项目，或写入已有项目。

项目规则：

- 项目归档后从首页项目筛选中隐藏。
- 归档项目不会删除或解除其任务。
- 归档项目的任务继续显示在“全部”中，并保留项目归属信息。
- P0 不提供恢复已归档项目的用户入口；恢复能力列入 P1，底层数据必须保留。
- 首页项目筛选横条是可横向滚动的控件；最后一个项目 Chip 之后必须提供可点击的“管理项目”图标按钮，打开项目管理 Bottom Sheet。该按钮不得与顶部“新建任务”加号复用，并具备可访问名称。
- 项目颜色在创建时自动分配，P0 不提供手动选色。
- 项目标题和项目管理列表中的“N 个待办”只统计 status = pending 的任务。
- 项目页底部可以展示当前项目摘要卡，包括项目名称、待完成数、完成进度和归档入口；完成进度按已完成数 / 未删除任务总数计算。
- 项目摘要卡中的末端操作语义为“归档”，不得级联删除任务。点击设计稿中的末端图标后必须先展示标题为“归档项目”的确认界面，明确说明任务仍会保留在“全部”中；不得把该入口实现成项目或任务删除。
- 项目颜色只表达身份，不表达优先级。
- P0 不引入独立的“领域—目标—项目”多层结构。

### 4.6 P0-05 文字与语音输入

文字输入：

- 用户可以输入模糊目标、明确任务或管理命令。
- 系统可以展示可点击示例，但示例必须可编辑。
- 点击示例只将内容填入输入框，不立即发送、不调用模型、不扣积分。
- 点击“取消”关闭输入浮层，不调用模型、不扣积分。
- 用户点击“发送”后进入 AI 积分校验；校验通过才调用模型并进入同一 AI 对话浮层。

语音输入：

- 支持开始、停止、重试和继续处理。
- 将识别结果展示给用户。
- “重新说”丢弃当前转写并重新采集；“继续处理”确认转写并进入文本 Agent 流程。
- 语音只是输入适配器，不建立独立业务逻辑。
- 麦克风权限被拒绝时提供权限说明和文字输入入口，不得阻断手动任务管理。
- ASR 失败时保留文字输入入口。
- ASR 是否扣分取决于其接口是否实际调用已绑定积分成本的 AI/模型 API。

### 4.7 P0-06 AI 对话浮层与四类内容

| 语义标识 | 名称 | 作用 | 是否写入业务数据 |
|---|---|---|---|
| user_input | 用户输入 | 记录用户文本、语音转写或选择结果 | 否 |
| ai_reply | AI 文字回答 | 解释理解、说明下一步、返回结果或提供非执行性建议 | 否 |
| question | AI 问答/候选选择卡 | 在意图、必要信息或目标对象不明确时让用户补充或选择 | 否 |
| action_confirm | AI 操作确认卡 | 展示即将执行的写操作及影响，等待用户确认或取消 | 仅确认后写入 |

设计稿中的 Type 1 至 Type 4 编号只作为组件标注，不构成业务规则。产品、接口、数据模型和验收均以上述语义标识为准。

通用规则：

- 对话浮层包含固定标题区、可滚动消息区和固定输入区。
- 用户可以随时继续补充、修正或关闭。
- 关闭或下拉浮层只表示暂时离开，不产生写入，也不等于取消；待确认草稿保持 awaiting_confirmation，可从 Smart Inbox 恢复。
- 对话上下文必须在当前会话中保持一致。
- 用户选择问答或候选项后，该结果作为一条用户输入追加到当前会话，并携带既有上下文继续 Agent 判断；信息仍不足时允许继续提问。
- 候选卡必须提供“都不是”或自由补充入口，不得强迫用户在错误候选中选择。
- 回执必须区分“草稿已生成”和“操作已成功执行”。

### 4.8 P0-07 目标澄清与批量任务拆解

#### 输入适配

Agent 必须处理从高度模糊到相对明确的目标：

- 高模糊示例：“我今天要去露营。”
- 中模糊示例：“周末两个人自驾露营，装备还没买齐。”
- 低模糊示例：“帮我创建买帐篷、订营地、准备食物三个待办。”

#### 澄清规则

- 当缺失信息会显著改变任务清单时，Agent 应通过 AI 选择/澄清卡提问。
- 当信息已经足够时，Agent 应直接生成草稿，避免无意义追问。
- 用户可以选择暂不补充非必要信息，并要求先生成草稿。
- Agent 不得把推测内容伪装为用户已经提供的事实。

#### 计划拆解确认卡

计划拆解确认卡是 Action 确认卡的批量创建形态，至少包含：

- 建议的项目名称，或建议写入的已有项目；
- 待办项列表；
- 每项待办的标题；
- AI 推荐优先级；
- 用户已明确提供的截止或提醒信息；
- 对不确定内容的明确标识。

用户可以：

- 修改项目选择；
- 修改任务标题和优先级；
- 删除不需要的任务；
- 点击“再改一下”继续对话，要求整体调整；
- 关闭浮层并稍后从 Smart Inbox 继续；
- 点击“创建 N 项”确认创建。

确认规则：

- 未确认前不得创建项目或任务。
- 用户在该卡片中完成审阅后，点击“创建 N 项”直接进入原子写入，不再增加第二层重复确认。
- 批量确认必须采用原子执行；失败时不得残留部分任务。
- 成功后返回任务首页，并显示创建结果和撤销入口。

### 4.9 P0-08 AI 任务管理 Action

MVP 支持以下 Agent Action：

| Action | 说明 | 对象不明确时 |
|---|---|---|
| 创建单个任务 | 创建一项明确待办 | 追问项目或必要字段 |
| 创建项目及任务批次 | 将目标拆解结果批量写入 | 展示完整计划草稿 |
| 整理待办 | 为一个或多个待整理任务建议项目归属，并可同时建议 scheduled_at 和 reminder_at | 展示候选或批量 Action 确认卡 |
| 修改任务 | 修改标题、项目、描述、优先级、计划执行时间、截止或提醒 | 展示候选任务供选择 |
| 标记完成 | 将待完成任务改为已完成 | 展示候选任务供选择 |
| 恢复任务 | 将已完成任务恢复为待完成 | 展示候选任务供选择 |
| 软删除任务 | 将任务移出活动列表 | 展示候选任务供选择 |

MVP 中，上述所有 Agent Action 均必须经过 Action 确认卡。不存在“置信度高所以直接执行”的例外。

“整理待办”确认卡必须逐任务、逐字段展示 project_id、scheduled_at 和 reminder_at 的变化前后值；只建议需要补充或用户明确要求调整的字段，不得静默覆盖已有时间或提醒。一次确认可以原子写入多项字段，用户也可以在确认前删除单项建议。

### 4.10 P0-09 Action 确认卡

Action 确认卡必须展示：

- 面向用户的操作标题；
- 可审计的 Action 类型；
- 操作对象及其项目归属；
- 将变化的字段；
- 变化前与变化后；
- 执行后用户将在界面中看到的结果；
- “继续修改/继续对话”；
- “确认执行”；
- 关闭入口；业务需要时可提供明确的取消操作。

执行规则：

1. 确认卡是所有 AI 写操作的唯一写入网关。
2. 关闭浮层不改变 Action 状态；用户明确取消后，Action 才进入 cancelled。
3. 用户继续对话并形成新草稿后，旧 Action 进入 superseded。
4. 用户确认时，系统必须重新校验对象和当前数据版本。
5. 对象已变化或已不存在时，不得套用旧草稿；应提示用户重新确认。
6. 重复点击确认不得产生重复任务或重复变更。
7. 执行成功后才可发送成功回执。
8. 执行失败时保留上下文，明确提示失败，不得伪装成功。
9. 可逆操作应提供撤销；撤销本身必须可审计。

### 4.11 P0-10 Smart Inbox

Smart Inbox 是首页顶部常驻的 AI 入口和状态摘要，用于维持产品的 AI 心智；用户可以将其折叠。它可以承担氛围作用，但可操作内容必须对应真实流程。

P0 可展示的状态：

- 默认 AI 入口；
- 有待用户回答的澄清问题；
- 有未确认的计划或 Action 草稿；
- 检测到待完成任务缺少项目归属、计划时间或提醒，可建议整理；
- 当前项目的任务整理入口；
- 当前范围没有待完成任务时的新事项入口；
- 最近一次 AI 执行失败，需要继续处理；

规则：

- 每次只突出一个最需要用户处理的状态。
- 状态文案必须具体，例如“有 1 个计划等待确认”。
- 点击后进入对应对话位置。
- 没有待处理状态时展示通用 AI 入口；用户主动折叠后保留折叠状态。
- Smart Inbox 在“全部”、项目筛选和空状态中均保留，并根据当前筛选范围调整文案和入口行为。
- P0 不在 Smart Inbox 中主动替用户生成每日优先事项。
- “缺少项目/计划时间/提醒”检测优先使用确定性数据规则，不调用模型、不扣积分；只有用户点击“一键整理”后生成归属、时间或提醒建议等确需调用模型的步骤才进入积分校验。
- Smart Inbox 中的“一键整理”等按钮只能进入澄清、草稿或确认流程，不得成为绕过 Action 确认卡的直接写入入口。

### 4.12 P0-11 反馈、撤销和异常

必须覆盖：

- 创建成功；
- 修改成功；
- 完成和恢复成功；
- 删除成功；
- 批量执行失败；
- Action 已过期或对象冲突；
- 网络或 Agent 服务异常；
- 语音识别失败；
- AI 积分不足、积分校验失败或 AI 服务暂不可用。

反馈规则：

- 成功反馈不阻塞主要流程。
- 创建、完成、恢复和软删除等可逆操作提供撤销。
- 服务不可用时允许用户继续使用手动待办功能。
- AI 积分不足时展示最终 UI 中的“智能处理暂不可用”降级浮层，不调用模型，不改变任务数据。
- MVP 用户侧不展示 AI 积分余额、单次积分成本、Token、模型成本、充值入口或技术错误堆栈。

### 4.13 P0-12 评测与审计

为未来开放“特定 Action 直接执行”，P0 必须从第一天记录结构化数据：

- 用户原始输入及输入方式；
- Agent 识别的意图和 Action 类型；
- 是否触发澄清及澄清轮次；
- 候选对象及最终用户选择；
- AI 生成的原始 Action 草稿；
- 用户对草稿的编辑、删除或补充；
- 用户确认、明确取消或关闭浮层（dismiss）；
- 执行结果、错误类型和耗时；
- 是否撤销；
- 模型、提示词和工具版本；
- 线上人工标注或离线评测关联标识。

直接执行能力不属于 P0。P0 只负责建立可评估基础。

### 4.14 P0-13 基础隐私与无障碍

P0 必须提供以下基础保障：

- 项目、任务、会话、Action、撤销记录、AI 积分余额与积分流水按用户严格隔离。
- 用户退出后不继续展示个人任务内容。
- 评测数据遵循最小必要原则，并尽可能去标识化。
- 原始语音默认不长期保存。
- 项目、优先级和操作状态不只依赖颜色表达。
- 图标按钮具备可访问名称，关键控件具备清晰焦点状态。
- Action 确认卡明确说明“确认前不会修改数据”。

### 4.15 P0-14 AI 积分与接口计费

AI 积分是 P0 的后端业务额度。所有会调用 AI 或模型 API 的产品功能接口必须绑定积分成本，并在模型调用前调用独立、统一的积分校验接口。积分校验接口负责校验、幂等和预占；业务接口不得自行读取余额后绕过该接口调用模型。

#### 能力接口绑定

每个 AI 能力接口必须配置：

- 唯一 capability_code；
- 唯一 endpoint_code；
- 是否调用 AI/模型 API；
- 单次产品级 AI 请求所需积分；
- 成本规则版本；
- 启用/停用状态。

一次产品级 AI 请求可以包含意图识别、生成和内部重试，但必须共享同一个 request_id，不得因内部实现拆分而重复扣分。用户主动重新生成、继续要求 AI 修改，或回答澄清后再次发起模型调用，属于新的产品级 AI 请求，可按绑定规则再次扣分。

#### 调用前校验

1. 功能接口在调用模型前，先携带 user_id、capability_code、endpoint_code 和 request_id 调用统一积分校验接口。
2. 校验接口确认能力已启用、成本规则有效，并以 `User.ai_points - 同用户全部有效预占` 计算本次可用额度。
3. 校验和预占必须是一个原子操作；校验通过后返回 reservation_id，同一 request_id 重试时返回同一有效预占，不得重复占用。
4. 余额不足或校验服务不可用时，不得调用模型，也不得产生扣分，并返回“智能处理暂不可用”状态。
5. 业务接口只能持有效 reservation_id 调用目标模型；单纯读取余额不构成调用许可。
6. 可用 AI 结果成功持久化后，系统按 reservation_id 幂等结算：原子扣减 User.ai_points、将预占转为成功 debit 流水，并释放预占额度。
7. 系统或模型失败且未形成可用结果时，系统释放预占，不改变 User.ai_points；若未来采用先扣后调模式，则必须以独立 refund 流水恢复余额。
8. 结算暂时失败时保留预占并幂等重试，不得再次调用模型或重复生成结果；只有结算成功后才向客户端返回可消费的 AI 结果。
9. 每个预占必须有失效时间并进入故障回收：失效时没有可用结果则自动释放；已经持久化可用结果则优先继续幂等结算，不得直接释放后形成未计费结果。
10. 任意时刻必须满足 `User.ai_points >= 全部有效预占积分之和`；expire 和负向 adjustment 只能消耗未预占额度，额度不足时必须延后或拒绝该变更。

#### 扣分规则

- 不调用 AI/模型 API 的行为不扣分，包括手动任务 CRUD、列表刷新、打开已有会话、查看 Smart Inbox、Action 确认/取消、数据库写入和撤销。
- AI 返回的可用结果经校验并成功持久化后，按接口绑定成本结算预占并生成积分流水。
- “可用结果”包括可展示的 AI 文字回答、问答/候选卡、计划拆解确认卡或 AI 操作确认卡。
- AI 已成功产出可用结果后，用户关闭对话、取消 Action 或拒绝创建任务，积分不退。
- 系统或模型失败且没有形成可用结果时不产生最终扣分；预占直接释放，已经成功入账的异常扣分只能通过等额 refund 流水补偿。
- 同一 request_id 因重复点击、网络重试或服务重放，最多成功扣分一次。
- Action 确认后的任务/项目写入如果不再调用模型，不产生第二次 AI 扣分。
- 语音转写只有在实际调用已绑定积分成本的 AI/模型接口时才扣分；设备本地转写等非模型能力不扣分。

#### 用户侧呈现

- MVP 不展示 AI 积分余额、积分流水和单次成本。
- MVP 不提供购买、充值或套餐入口。
- 余额不足时只展示通用不可用状态，并保留所有手动待办能力。
- 当用户因当日可用积分耗尽进入最终 UI 的额度浮层时，可展示“今日智能处理次数已达体验上限，明天可继续使用”；该文案由每日补足规则保证，不展示具体积分或成本。
- 页面启动和 Smart Inbox 后台检查不得静默触发收费模型调用。

#### 积分发放与每日补足

- 新用户账户的 ai_points 字段从 0 建立，随后按当前有效的“新用户初始赠送”规则写入一笔 grant 流水，并在同一原子事务中增加余额。
- 新用户赠送积分必须通过流水发放，不得通过非零数据库默认值或后台直接改余额实现。
- 为匹配最终 UI 中“明天可继续”的承诺，P0 采用每日补足：进入新的用户本地自然日后，系统将已入账余额补足到配置的每日体验额度；高于该额度时不扣减，未使用余额不因补足而过期。
- 每日补足通过一笔 reason_code = daily_allowance_top_up 的 grant 流水完成，并与余额原子更新；同一 user_id 和本地日期最多成功一次，流水同时保存所用规则版本。可以由定时任务执行，也可以在当日首次 AI 请求校验前惰性执行，但不得调用模型或消耗积分。
- 注册当天只执行新用户初始赠送，从下一本地自然日起参与每日补足，避免同一天重复获得两类初始化额度。
- 初始赠送量、每日体验额度、各能力成本和后续过期规则属于可配置运营参数；具体数值在上线运营评审前确定，不影响本 PRD 的校验、预占、结算和审计框架。
- 初始赠送或每日补足失败时不得形成账实不一致；手动待办能力仍可使用，AI 能力按通用不可用状态降级。

### 5.1 P1：核心闭环增强

## 6. MVP 业务流程

### 6.1 总体业务流程

    用户进入任务首页
        ↓
    选择操作路径
        ├─ 手动新建/管理
        │    → 保存业务数据
        │    → 刷新当前列表、数量和摘要
        │    → 不调用模型、不扣 AI 积分
        │
        └─ 通过文字/语音调用 AI
             → 识别目标能力接口并调用积分校验与预占
                 ├─ 校验失败
                 │    → 不调用模型、不扣积分
                 │    → 展示“智能处理暂不可用”并保留手动入口
                 │
                 └─ 校验通过并取得 reservation_id
                      → 调用 Agent 识别并分类意图
                      → 保存本次可用 AI 结果并结算预占
                          ├─ 非写入咨询
                          │    → 展示 AI 文字回答 → 继续或结束对话
                          │
                          ├─ 信息或对象不明确
                          │    → 展示问答/候选选择卡
                          │    → 用户选择或补充
                          │         ├─ 结构化信息已足够
                          │         │    → 确定性生成下一张卡，不调用模型、不扣积分
                          │         └─ 仍需模型判断
                          │              → 生成新 request_id，重新校验与预占后调用模型
                          │
                          ├─ 计划拆解
                          │    → 展示可编辑的计划拆解确认卡
                          │
                          └─ 明确写操作
                               → 展示 AI 操作确认卡

    计划拆解确认卡与 AI 操作确认卡进入统一的确认结果分支
        ├─ 本地编辑计划项 → 只更新草稿，不调用模型、不扣积分
        ├─ 要求 AI 修改 → 返回对话，以新 request_id 重新校验、预占和调用模型
        ├─ 关闭 → 不写业务数据，保留待确认草稿，已结算积分不退
        ├─ 明确取消 → 不写业务数据，草稿取消，已结算积分不退
        └─ 确认
             ├─ 计划拆解卡 → 原子创建项目及 N 项任务，不出现第二层确认
             └─ AI 操作卡 → 重校验对象与版本后写入任务/项目

### 6.2 目标拆解流程

1. 用户提交模糊目标。
2. Agent 判断哪些缺失信息会影响任务方案。
3. 若需澄清，展示 AI 选择/澄清卡。
4. 用户选择选项或自由输入补充信息。
5. 若下一步需要再次调用模型，系统重新执行积分校验；校验通过后生成计划拆解确认卡。
6. 用户逐项检查、编辑、删除，或点击“再改一下”要求重做。
7. 手动编辑卡片不调用模型、不扣分；要求 AI 重做属于新的 AI 请求。
8. 用户在计划拆解确认卡中点击“创建 N 项”。
9. 系统以一个事务创建项目及任务，不再增加第二层确认。
10. 首页切换到对应项目或“全部”，展示新任务。
11. 系统显示成功反馈并提供撤销。

### 6.3 AI 管理任务流程

1. 用户输入“把买帐篷设成高优先级”。
2. 系统为本次产品级 AI 请求执行积分校验与预占，取得 reservation_id 后调用 Agent。
3. Agent 在当前用户的有效任务范围内检索对象并识别操作意图。
4. 若唯一匹配，Agent 生成修改优先级的 AI 操作确认卡；卡片持久化后结算本次预占。
5. 若存在多个候选，Agent 生成 AI 选择卡；选择卡持久化后结算本次预占，用户可以选择目标或点击“都不是”继续补充。
6. 用户选择结构化候选后，如果系统可确定性生成 AI 操作确认卡，则不再次调用模型或扣分；若补充内容仍需模型理解，则以新 request_id 重新完成积分校验、预占、模型调用和结果结算。
7. 用户确认后，系统重校验任务与版本并执行；确认和数据库写入本身不调用模型、不再扣分。
8. 返回列表并展示变更结果。

### 6.4 手动管理任务流程

1. 用户在列表中点击任务完成控件，或打开任务编辑浮层。
2. 完成控件直接改变状态，并提供撤销。
3. 编辑浮层只有在用户点击保存后才持久化。
4. 删除采用软删除，并提供撤销。
5. 手动操作不经过 Agent，也不需要 Action 确认卡。
6. 保存成功后自动刷新当前列表、任务数量和页面摘要；失败时保留表单。

### 6.5 Smart Inbox 流程

1. 系统使用业务状态和确定性规则检查待澄清、待确认、待办缺少项目/计划时间/提醒或失败恢复。
2. 若存在多个状态，按“待确认 > 待澄清 > 失败恢复 > 待办整理”确定展示。
3. 用户点击状态卡，回到对应对话位置。
4. 用户点击“一键整理”后，若需要调用模型，则先执行积分校验并生成可确认草稿；草稿可同时建议项目归属、scheduled_at 和 reminder_at，并逐字段展示变化。确定性整理不扣分。
5. 状态被解决后，卡片更新或收起。
6. 无待处理状态时展示通用 AI 入口；用户折叠后以紧凑状态保留。

### 6.6 Action 状态流

    草稿生成
        ↓
    等待确认
        ├─ 用户本地编辑计划项 → 更新当前草稿，仍为等待确认
        ├─ 用户要求 AI 修改且新草稿生成成功 → 旧草稿失效 → 新草稿等待确认
        ├─ 用户关闭浮层 → 保持等待确认，可从 Smart Inbox 恢复
        ├─ 用户明确取消 → 已取消
        └─ 用户确认 → 执行中
                         ├─ 成功 → 已执行
                         └─ 失败 → 执行失败，可重试或重新生成

任何已失效、已取消或已执行的 Action 不得再次执行。

### 6.7 AI 积分校验与结算流程

    产品功能请求
        ↓
    判断目标接口是否调用 AI/模型 API
        ├─ 否 → 继续业务流程，不进入积分接口、不扣积分
        └─ 是 → 若进入新的用户本地自然日，先幂等执行每日额度补足
                  → 读取接口绑定的有效能力和成本规则
                  ↓
               调用统一积分校验与预占接口
                  ├─ 余额不足/校验失败
                  │    → 不调用模型、不扣积分
                  │    → 展示通用不可用状态
                  └─ 原子校验并预占成功
                       → 返回 reservation_id → 调用模型
                           ├─ 未形成可用结果
                           │    → 释放预占，User.ai_points 不变
                           └─ 可用结果已持久化
                                → 按 reservation_id / request_id 幂等结算
                                → 原子扣减余额并写入 succeeded debit 流水
                                → 用户后续关闭、取消或拒绝不退款

    若已成功入账后发现系统性错扣
        → 新建 succeeded refund 流水并原子恢复余额
        → 原 succeeded debit 保持不变，二者通过 reversal_of_id 关联

## 7. 用户完整操作动线示例

### 7.1 示例 A：从模糊目标到完成露营准备

#### 首次进入

1. 用户注册并登录；系统按有效规则通过 grant 流水完成初始积分发放，余额与发放流水原子写入，用户侧不展示具体积分。
2. 用户进入空任务首页，能够识别项目筛选、任务列表区域和底部 AI 输入。
3. 页面不自动播放首次引导或打开对话；用户主动点击 Smart Inbox 或底部 AI 输入入口。
4. 用户输入：“我这周末想去露营。”

#### AI 澄清

5. 系统完成本次 AI 能力积分校验后调用模型；AI 回复其理解，并询问会显著影响计划的信息，例如出行人数、过夜与否、交通方式、是否已有装备。
6. AI 问答卡作为可用结果保存，本次请求按绑定规则扣分。
7. 用户通过选择卡回答：“两个人，自驾，过夜，没有装备。”
8. 若回答后需要再次调用模型，系统为新的 AI 请求重新校验积分；AI 根据补充信息生成“周末露营”计划拆解确认卡。

#### 用户审阅

9. 该卡建议新建“周末露营”项目，并列出订营地、确认天气、购买或租赁帐篷、准备睡眠装备、准备食物和检查车辆等任务。
10. 每项任务展示推荐优先级；推荐被明确标识为 AI 建议。
11. 用户手动删除不需要的一项，并把“订营地”调整为高优先级；这些本地编辑不调用模型、不扣分。
12. 计划拆解确认卡同步更新将创建的项目和任务数量，此时首页仍没有任何新项目或新任务。

#### 确认与落地

13. 用户在计划拆解确认卡中点击“创建 N 项”。
14. 系统原子创建“周末露营”项目及确认后的任务，不再次调用模型或扣分。
15. 首页展示新任务，并提示创建成功和可撤销。

#### 后续管理

16. 次日用户直接进入任务首页，系统不自动打开 AI 对话。
17. 用户手动将“确认天气”标记完成。
18. 用户说：“帐篷已经买了，把买帐篷完成；燃料还没买，改成高优先级。”
19. 系统完成新的积分校验后，Agent 找到对应任务并生成包含两项变化的 AI 操作确认卡；卡片保存为可用结果后完成扣分。
20. 用户检查后确认，系统执行并更新列表。
21. 用户继续处理任务，已完成项进入底部折叠区。
22. 当所有相关任务处理完毕时，P0 只反映任务状态；不自动宣称目标已经达成。

### 7.2 示例 B：模糊管理指令

1. 用户输入：“周报处理一下。”
2. Agent 无法确定用户是想新建、完成还是调整优先级。
3. 系统展示 AI 选择卡：
   - 标记已有周报完成；
   - 新建周报待办；
   - 调整周报优先级。
4. 用户选择“标记已有周报完成”。
5. 若存在多个周报任务，系统继续展示候选任务。
6. 用户选定“工作 / 写周报”。
7. 系统展示 Action 确认卡：“待完成 → 已完成”。
8. 用户确认后，任务进入已完成折叠区并出现撤销入口。

### 7.3 示例 C：取消和失败保护

1. 用户要求批量创建任务。
2. AI 生成计划草稿。
3. AI 已形成可用结果，本次积分已经扣除。
4. 用户关闭浮层，系统不创建任何任务数据，但草稿保持“等待确认”而不是被取消。
5. 用户重新打开 Smart Inbox，可继续处理未确认草稿。
6. 用户确认时发现网络中断。
7. 系统提示执行失败，列表中不出现部分任务；由于 AI 结果此前已经产出，本次任务写入失败不退还 AI 积分。
8. 用户恢复网络后可重新确认；幂等校验保证不会重复创建，也不会重复扣分。

### 7.4 示例 D：AI 积分不足时降级

1. 用户输入一个需要调用 AI 的目标。
2. 目标能力接口先调用统一积分校验。
3. 校验发现余额不足，系统不调用模型、不扣分。
4. 若原因为当日体验额度耗尽，页面展示“今日智能处理次数已达体验上限，明天可继续使用”；其他校验失败展示“智能处理暂不可用”，两者都不展示具体积分余额或成本。
5. 用户关闭提示后，仍可通过顶部加号和任务编辑浮层手动创建、编辑和完成任务。
6. 进入下一用户本地自然日后，系统通过幂等 grant 流水补足每日体验额度，用户可以再次发起 AI 请求。

### 8.1 最终 UI 交互补充

- 任务行左侧展示计划执行时间和项目，中部展示标题、Deadline 与提醒，右侧展示优先级和完成控件。
- 完成控件是手动操作；点击后任务进入当前范围的已完成折叠区，并显示撤销 Toast。
- 撤销 Toast 消失后，用户仍可展开已完成区并恢复任务。
- 空状态表示当前筛选范围待完成数为 0，不代表账号没有项目、已完成任务或 AI 会话。
- 文本推荐语句先填入输入框；只有点击“发送”才进入 AI 积分校验。
- 语音页“重新说”重置当前转写，“继续处理”确认转写并进入 Agent。
- 候选或问答卡允许选择候选、选择“都不是”或自由补充；提交后作为用户输入继续同一会话。
- 计划拆解确认卡中的 N 随任务删除动态变化；“再改一下”返回对话，“创建 N 项”直接执行批量写入。
- AI 操作确认页的“继续对话”不写入；“确认执行”才更新任务/项目并刷新列表。
- 项目管理页提供新建、改名和归档；项目颜色自动分配，数量为待完成任务数。设计稿中的末端图标只打开“归档项目”确认界面，图标可访问名称、确认标题和说明文案均使用“归档”，不得使用“删除”。
- “智能处理暂不可用”页的“知道了”只关闭浮层并返回任务首页，不调用模型、不扣积分。

## 9. 数据对象模型

### 9.1 建模原则

1. 以下为产品概念模型，不等同于数据库物理表。
2. 所有用户业务数据必须归属于唯一用户；AiCapability 属于全局能力配置，AiPointTransaction 必须归属于唯一用户。
3. P0 不建立独立“领域”和“目标”层级。
4. P0 使用“项目”承接轻量分组，使用“会话 + Action 草稿”保留目标的生成上下文。
5. Smart Inbox 是业务状态的聚合视图，P0 不要求单独持久化为实体。
6. 所有 AI 写入必须能追溯到用户确认的 Action。
7. 所有持久化数据对象必须包含 extra: Object（obj），默认值为 {}。
8. extra 只承载非核心扩展信息；参与 P0 业务规则、筛选、约束、计费和审计的字段必须建模为正式字段，不得全部写入 extra。
9. User.ai_points 保存当前已入账余额；用户可用额度还需扣除有效预占。任何余额变化必须同时产生可追溯的 succeeded AiPointTransaction，不允许无流水直接改余额。

### 9.2 对象关系

    User
      ├─ 0..N Project
      ├─ 0..N Task
      ├─ 0..N ConversationSession
      │       ├─ 1..N Message
      │       └─ 0..N ActionProposal
      │                 ├─ 1..N ActionMutation
      │                 └─ 0..1 ActionExecution
      ├─ 0..N UndoOperation
      ├─ 0..N AgentEvaluationEvent
      └─ 0..N AiPointTransaction

    Project 0..1 ── 0..N Task
    ActionExecution 0..1 ── 0..1 UndoOperation
    AiCapability 0..1 ── 0..N AiPointTransaction
    AiPointTransaction 0..1 ── ConversationSession / Message / ActionProposal

| name | String | 能力名称 |
| calls_model_api | Boolean | 是否实际调用 AI/模型 API |
| points_cost | Integer | 单次产品级请求积分成本 |
| cost_rule_version | String | 成本规则版本 |
| status | active / inactive | 能力是否可用 |
| effective_at | DateTime | 规则生效时间 |

- capability_code、endpoint_code 和 cost_rule_version 组合唯一；同一能力与接口在任一时刻最多只有一个生效版本。
- 成本变更必须产生新规则版本，历史流水保留当时使用的能力配置和成本快照。
- 一个产品级 AI 请求只使用一个 request_id；内部模型重试不得生成多笔成功扣分。

### 9.14 AiPointTransaction：AI 积分流水

| 字段 | 类型/枚举 | 说明 |
|---|---|---|
| id | ID | 流水唯一标识 |
| user_id | ID | 所属用户 |
| request_id | String，可空 | 产品级 AI 请求 ID；系统发放或人工调整时可空 |
| idempotency_key | String，唯一 | 防止重复扣分、退款或发放 |
| reservation_id | String，可空，唯一 | 调用前预占标识；debit 必填，其他交易可空 |
| transaction_type | debit / grant / refund / adjustment / expire | 扣除、发放、退款、调整或过期 |
| status | pending / succeeded / failed / cancelled | 流水或预占状态 |
| points_delta | Integer | 有符号积分变化；debit/expire 为负数，grant/refund 为正数 |
| capability_id | ID，可空 | 关联的能力成本配置版本；debit 必填 |
| balance_before | Integer，可空 | 成功入账前余额；pending/failed/cancelled 可空 |
| balance_after | Integer，可空 | 成功入账后余额；pending/failed/cancelled 可空 |
| capability_code | String，可空 | 关联 AI 能力 |
| endpoint_code | String，可空 | 关联功能接口 |
| cost_rule_version | String，可空 | 本次使用的成本规则版本 |
| session_id | ID，可空 | 关联会话 |
| message_id | ID，可空 | 关联可用 AI 结果 |
| proposal_id | ID，可空 | 关联 Action 草稿 |
| reversal_of_id | ID，可空 | refund 对应的原 succeeded debit |
| reason_code | String，可空 | 发放、失败、退款或调整原因 |
| grant_period_date | Date，可空 | 每日补足所属的用户本地自然日 |
| grant_rule_version | String，可空 | 发放或补足规则版本 |
| reserved_at | DateTime，可空 | 预占成功时间 |
| reservation_expires_at | DateTime，可空 | 预占失效时间；pending debit 必填 |
| settled_at | DateTime，可空 | 最终入账时间 |
| released_at | DateTime，可空 | 未结算预占的释放时间 |
| created_at | DateTime | 创建时间 |
| extra | Object（obj） | 扩展字段，默认 {} |

积分约束：

- pending debit 表示有效预占：它占用可用额度，但尚未改变 User.ai_points；结算时原子转为 succeeded 并实际扣减余额，释放时转为 cancelled 且不改变余额。
- pending debit 超过 reservation_expires_at 后必须由故障回收任务处理：没有持久化可用结果时转为 cancelled；已有结果时继续幂等结算。不得让孤儿预占永久冻结额度。
- User.ai_points 必须等于账户初始值加全部 succeeded 流水的 points_delta；pending、failed 和 cancelled 不计入已入账余额。
- User.ai_points 必须始终大于或等于全部 pending debit 的绝对值之和；expire 和负向 adjustment 只能使用扣除有效预占后的余额。
- 同一 request_id、capability_code 和扣分语义最多存在一笔 pending 或 succeeded debit；接口重试复用原 reservation_id。
- 任一 debit 均必须包含 request_id、reservation_id、capability_id、capability_code、endpoint_code 和 cost_rule_version；pending 阶段先保存成本快照，成功结算后不得随配置更新而改变。
- succeeded debit 必须包含 request_id、reservation_id、capability_id、capability_code、endpoint_code、cost_rule_version，以及至少一个可用结果关联；这些字段是当次成本快照，不随配置更新而改变。
- grant、adjustment 和 expire 可以不关联 AiCapability；新用户初始积分必须由 reason_code = new_user_initial_grant 的 succeeded grant 发放。
- 每日补足必须由 reason_code = daily_allowance_top_up 的 succeeded grant 发放，并包含 grant_period_date 和 grant_rule_version；同一用户和 grant_period_date 最多成功一笔，规则版本只作当次快照。
- refund 必须为正数、包含 reversal_of_id，并关联一笔 succeeded debit；P0 只支持全额退款，金额必须等于原 debit 的绝对值，每笔 debit 最多存在一笔 succeeded refund，成功 refund 的 reversal_of_id 唯一。退款以新的 succeeded 流水入账，原 debit 永久保持 succeeded，不修改、不覆盖、不删除。
- 余额更新与 succeeded 流水写入必须在同一原子事务中完成。

### 9.15 Smart Inbox 派生状态

Smart Inbox 不作为独立主数据对象，按以下数据计算：

| 状态 | 数据来源 |
|---|---|
| 待澄清 | Message.message_type = question 且 interaction_status = pending |
| 待确认 | ActionProposal.status = awaiting_confirmation |
| 待办整理建议 | status = pending 且按已配置的确定性规则判定需要补充项目、计划时间或提醒；字段为空只是候选条件，不要求每个空字段都触发建议，也不在后台生成 AI 内容 |
| 当前项目入口 | 当前筛选 Project + pending 任务统计 |
| 当前范围已清空 | 当前筛选范围 pending 任务数 = 0 |
| 执行失败 | ActionProposal/ActionExecution.status = failed |
| 通用 AI 入口 | 上述状态均不满足时，保留 Smart Inbox 的默认入口内容 |

## 10. 核心业务规则

| 编号 | 规则 |
|---|---|
| BR-01 | AI 只提供工具和建议，最终决定权属于用户。 |
| BR-02 | 所有 AI 写操作必须先生成 Action 确认卡。 |
| BR-03 | 用户通过明确 UI 控件发起的手动操作不经过 AI 确认卡。 |
| BR-04 | 未确认、取消或过期的 Action 不得写入业务数据；关闭浮层不等于取消，待确认草稿可恢复。 |
| BR-05 | 无法唯一定位任务时必须澄清或提供候选，不得猜测执行。 |
| BR-06 | 批量创建必须原子执行，避免部分成功。 |
| BR-07 | AI 建议的优先级可编辑，用户确认后才成为正式数据。 |
| BR-08 | 无项目任务只在“全部”中显示。 |

| BR-11 | 包括首次进入在内，所有已登录用户默认不自动打开对话浮层或播放首次引导动效。 |
| BR-12 | Smart Inbox 在全部、项目和空状态中保留，允许折叠；无待处理状态时展示通用 AI 入口。 |
| BR-13 | AI 积分不足、校验失败或 AI 服务不可用时，手动任务管理必须继续可用。 |
| BR-14 | 成功回执只能在持久化成功之后出现。 |
| BR-15 | 置信度不能在 P0 中替代用户确认。 |
| BR-16 | 所有调用 AI/模型 API 的功能接口必须绑定能力成本，并在调用前通过统一接口原子完成积分校验与预占。 |

## 11. 验收标准

### AC-01 首次 AI 批量创建

给定一个没有任务的新用户，当其输入模糊目标并完成必要澄清后，系统能够展示可编辑的计划拆解确认卡；只有点击“创建 N 项”后，项目和任务才出现在首页，且不出现第二层重复确认。

### AC-02 取消不写入

给定一个等待确认的 Action：用户关闭浮层时业务数据不变且草稿仍可从 Smart Inbox 恢复；用户明确取消后草稿进入 cancelled；用户要求 AI 修改并形成新草稿后，旧草稿进入 superseded。本地编辑计划项只更新当前草稿，不触发 superseded。

### AC-03 模糊意图消歧

给定“周报处理一下”等无法唯一确定 Action 的指令，系统必须展示澄清选项；在用户选择前不得生成可执行写入。

### AC-04 对象候选选择

给定多个名称相似的任务，系统必须展示候选及项目上下文；用户选定后才能生成确认卡。

### AC-05 所有 AI 写操作确认

给定任一 P0 Agent Action，执行前必须出现包含目标、字段变化和结果影响的确认卡；不存在绕过路径。

### AC-06 手动任务闭环

用户可以手动新建、编辑、完成、恢复和软删除任务，数据跨会话保留，完成与删除可撤销。

### AC-07 项目筛选和归档

无项目任务仅在“全部”显示；项目标题和管理页数量只统计待完成任务；项目归档后从筛选中消失，但其任务仍在“全部”可见；P0 不提供恢复入口。

### AC-08 语音降级

语音识别结果可重试或修正，并进入同一文本 Agent 流程；麦克风权限拒绝或语音失败不影响文字输入和手动管理。

### AC-09 进入不打断

任何已登录用户，包括第一次进入和再次进入，均默认看到任务首页且不自动弹出对话或播放首次引导动效；Smart Inbox 仍作为可折叠入口展示，并在存在待处理状态时提示继续处理。

### AC-10 执行一致性

批量执行失败时不产生部分数据；重复确认不产生重复数据；对象版本变化时要求重新确认。

### AC-11 失败与回执

执行失败时系统明确提示失败并保留上下文；没有实际成功写入时不得展示成功回执。

### AC-12 评测数据完整

每个 AI Action 都可以追溯到原始输入、模型/提示词/工具版本、草稿、用户修正、确认或取消、执行结果与撤销结果。

### AC-13 用户数据隔离

任何用户都无法读取或修改其他用户的项目、任务、会话、Action、AI 积分余额和积分流水。

### AC-14 AI 积分调用网关

给定任一需要调用 AI/模型 API 的功能接口，模型调用前必须通过统一接口原子完成积分校验与预占并取得 reservation_id；余额不足或校验失败时模型未被调用、积分不变，页面展示通用不可用状态，全部手动功能仍可使用。

### AC-15 AI 成功扣分与取消

AI 可用结果成功持久化后，只按目标接口绑定成本扣分一次并生成流水；用户随后关闭对话、取消 Action 或拒绝创建任务，业务数据不写入，但本次积分不退。

### AC-16 AI 失败不扣分

系统或模型失败且未形成可用结果时，pending 预占被释放且用户余额不减少；孤儿预占到期后也能自动判断“释放或继续结算”，不会永久冻结额度。如果异常情况下已有 succeeded debit，必须新建唯一的等额 succeeded refund，原 debit 保持不变。

### AC-17 非 AI 操作不扣分

手动新建、编辑、完成、恢复、删除、列表刷新、打开已有会话、Action 确认/取消和撤销均不调用模型，因此不改变 AI 积分。

### AC-18 积分幂等与账实一致

重复点击、网络重试和服务重放不会对同一 request_id 重复预占或扣分；并发请求只能在扣除其他有效预占后仍足额时通过。User.ai_points 可以由 succeeded 积分流水核对，且始终大于或等于全部有效预占之和。

### AC-19 扩展字段完整

User、Project、Task、ConversationSession、Message、ActionProposal、ActionMutation、ActionExecution、UndoOperation、AgentEvaluationEvent、AiCapability 和 AiPointTransaction 均包含默认 {} 的 extra: Object（obj）。

### AC-20 最终 UI 列表口径

首页和项目页标题中的 N 等于当前筛选范围待完成任务数；任务行能分别展示计划执行时间、Deadline 和提醒；当前范围无待完成任务时显示“今天已经清空”，同时保留 Smart Inbox、项目筛选和已完成区。

### AC-21 新用户积分发放

新账号建立时，ai_points 先以 0 初始化，再由唯一的 new_user_initial_grant 流水与余额在同一事务中完成发放；首次 AI 请求使用发放后的额度。重复注册回调或服务重试不重复赠送，赠送失败不产生账实不一致。

### AC-22 手动操作撤销

用户手动创建、完成、恢复或软删除任务后，系统生成 source_type = manual 的 UndoOperation；在有效期内点击撤销能够恢复原状态，重复点击不重复回滚，且全程不调用模型或扣分。

### AC-23 Smart Inbox 多字段整理

当确定性规则发现一批待整理任务时，Smart Inbox 可以展示“一键整理”；用户点击后若调用模型，必须先完成积分校验与预占。生成的 Action 确认卡可同时建议 project_id、scheduled_at 和 reminder_at，逐任务展示每个字段的前后值，用户确认前可删除单项建议，确认后原子写入。

### AC-24 项目管理入口可达

用户可以在项目横向栏滚动到最后，通过带“管理项目”可访问名称的独立图标按钮打开项目管理 Bottom Sheet；顶部加号始终只负责手动新建任务，普通项目 Chip 只负责筛选。

### AC-25 登录页演示数据隔离

未登录时，登录页待办卡只展示不可操作的静态演示内容且不发起真实任务查询；认证成功后只展示当前用户数据，退出后真实任务立即从未授权界面移除。

### AC-26 每日体验额度补足

从注册次日起，进入新的用户本地自然日后，系统把低于配置值的已入账余额补足到当日体验额度；同一用户和本地日期最多产生一笔 daily_allowance_top_up grant，高于额度时不扣减余额。前一日额度耗尽的用户次日能够再次使用 AI，页面仍不展示积分数字。

### 12.2 核心分析维度

- 输入方式：文字 / 语音 / 选择；
- 输入模糊度；
- Action 类型；
- 是否澄清；
- 澄清轮次；
- 草稿任务数量；
- 草稿编辑率和删除率；
- 确认率、取消率和撤销率；
- 执行成功率；
- capability_code、endpoint_code、request_id、积分成本和成本规则版本；
- 积分校验通过率、余额不足率、预占释放率、扣分成功率、退款率和新用户赠送成功率；
- 从 AI 创建到首次任务管理的时间；
- 不同模型、提示词和工具版本的表现。

### 12.3 未来直接执行的评测前置条件

任何 Action 从“必须确认”升级为“可直接执行”前，必须单独完成：

1. 明确的 Action 风险分级。
2. 离线标注集上的意图和对象识别评测。
3. 线上确认率、修正率、取消率和撤销率评估。
4. 错误可逆性评估。
5. 用户授权和关闭自动执行的入口设计。
6. 产品、Agent、数据和安全负责人共同审批。

具体阈值不在 MVP PRD 中预设。

## 13. 非功能性产品要求

### 13.1 数据正确性

- AI 确认与实际写入内容必须一致。
- 所有写入具备幂等保护。
- 批量操作具备事务性或等价回滚能力。
- 用户可见状态与服务端状态必须一致。
- User.ai_points 与 succeeded 积分流水必须账实一致，余额不得为负且不得小于有效预占总额；pending 预占只影响可用额度，不改变已入账余额。
- 同一 AI request_id 不得因重复点击、重试或服务重放重复预占或扣分。

### 13.2 隐私

- 用户任务和对话属于敏感个人数据。
- 传输与存储必须采用行业通行保护措施。
- Agent 评测只收集最小必要数据，并尽可能去标识化。
- 是否将内容发送给第三方模型提供商必须在隐私政策中透明说明。
- 原始语音默认不长期保存，除非用户明确授权且有必要用途。

### 13.3 可访问性

- 核心点击目标应该满足移动端可操作尺寸。
- 项目和优先级不得只通过颜色表达。
- 图标按钮必须有可访问名称。
- Bottom Sheet 打开后正确管理焦点，关闭后回到触发入口。
- Action 确认卡需要明确播报“确认前不会修改数据”。

### 13.4 降级能力

- AI、ASR、积分校验或额度服务不可用时，用户仍能查看和手动管理任务。
- 错误提示不暴露内部模型、Token、成本和技术堆栈信息。

## 14. 产品边界

### 14.1 始终必须

- 始终保留用户最终决定权。
- 始终对 AI 写操作展示确认卡。
- 始终记录 Action 的输入、确认和执行链路。
- 始终在收费模型调用前通过统一接口原子执行积分校验与预占，并为余额变化写入流水。
- 始终为失败提供明确状态，不静默吞错。
- 始终保证手动待办能力不依赖 AI 可用性。

### 14.2 扩大范围前必须评审

- 新增 Agent Action 类型。
- 新增或修改 AI 能力接口的积分成本、发放、过期或退款规则。
- 允许任一 Action 直接执行。
- 引入独立目标、领域或多层项目模型。
- 改变任务默认排序和首页信息架构。
- 长期保存语音、对话原文或将其用于模型训练。
- 增加第三方服务写操作。

### 14.3 明确禁止

- 未确认就执行 AI 写操作。
- 把 AI 推测描述成用户事实。
- 在对象不明确时猜测并修改。
- 绕过统一积分校验调用收费 AI/模型接口。
- 无积分流水直接修改 User.ai_points。
- 在 MVP 中把 AI 积分余额、单次成本、Token 或模型成本展示给普通用户。
- 删除项目时级联删除用户任务。
- 用 Smart Inbox 的视觉存在代替真实功能价值。

## 16. 发布判定

只有同时满足以下条件，MVP 才具备上线资格：

1. 用户能从一个模糊目标完整走通“澄清—草稿—确认—任务创建”。
2. 创建后的任务能被稳定查看、编辑、完成、恢复和软删除。
3. 所有 AI 写操作均不存在绕过 Action 确认卡的路径。
4. 取消、失败、重复点击和数据冲突不会造成错误或部分写入。
5. 包括首次进入在内，所有已登录用户默认进入待办首页，不自动弹出对话或播放首次引导动效。
6. Smart Inbox 在全部、项目和空状态中按最终 UI 保留，允许折叠，所有入口均进入真实流程。
7. Agent 评测和核心价值漏斗事件完整可用。
8. AI、语音或积分校验服务不可用时，手动待办管理仍可正常使用。
9. 新用户 grant、每日补足、积分校验与预占、成功扣分、失败释放/退款、并发幂等和账实一致性通过验收，且用户侧不展示余额和成本。
10. 所有持久化数据对象均具备默认 {} 的 extra: Object（obj）。
11. 项目管理入口、登录演示隔离、手动撤销和 Smart Inbox 多字段整理通过最终 UI 验收。
12. OD-02、OD-03、OD-04、OD-05、OD-06、OD-07 和 OD-09 已按 H0 决策实现；OD-08 在 H4 发布评审前冻结。
